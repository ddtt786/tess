# 10. 심화 실전: Ohm으로 만든 ES5(JavaScript) 파서 완전 분석

> 이 문서는 [00~09번 문서](./00-목차.md)를 모두 읽었다는 것을 전제로 합니다. 여기서는 Ohm 공식 저장소의 실전 예제인 **ES5(JavaScript) 문법**(`es5.ohm`)과, 그 문법을 활용하는 실제 자바스크립트 코드(`es5.js`)를 한 줄 한 줄 뜯어보면서, 지금까지 배운 개념들이 실제 프로덕션 수준의 파서에서 어떻게 조합되는지 확인합니다.

## 들어가며: 왜 이 예제가 중요한가

지금까지 만든 계산기 문법([04번 문서](./04-실전-예제-계산기-만들기.md))은 규칙이 10개도 안 되는 아주 작은 문법이었습니다. 반면 ES5 문법은 실제 JavaScript 언어 전체(정확히는 ECMAScript 5) 명세를 옮긴 것으로, 규칙이 100개가 넘습니다. 작은 예제에서는 잘 안 보이던 다음과 같은 것들이 이 문법에서는 명확하게 드러납니다.

- 연산자 우선순위가 **몇 단계까지** 깊어질 수 있는가
- 매개변수화된 규칙이 실제로 **문맥에 따라 문법이 달라지는 문제**(context-sensitive grammar)를 어떻게 해결하는가
- `_terminal` / `_nonterminal` / `_iter` 세 가지 특수 액션만으로 어떻게 **문법 전체를 커버**하는 시맨틱을 작성하는가
- `source` Interval을 이용해서 원본 코드를 **한 글자도 손실 없이 재구성**하는 방법
- 그래머 상속(`<:`)이 실제로 **strict/non-strict 모드**처럼 "같지만 살짝 다른 언어"를 표현하는 데 어떻게 쓰이는가

이 문서는 크게 두 부분으로 나뉩니다. **1~3부**는 `es5.ohm` 문법 파일을, **4~5부**는 그 문법을 사용하는 `es5.js`의 시맨틱 액션 코드를 다룹니다.

## 1부: 어휘 문법(Lexical Grammar) 분석

`es5.ohm`은 맨 위에 원본 출처를 명시하는 주석이 있습니다. Tom Van Cutsem의 es-lab 프로젝트를 바탕으로 Tony Garnock-Jones가 2014년에 Ohm용으로 옮긴 것이며, Apache License 2.0을 따릅니다. 실전 문법을 가져다 쓸 때는 이렇게 원본 출처와 라이선스를 명시하는 것이 좋은 관례라는 것도 함께 기억해두세요. ([05번 문서](./05-API-레퍼런스.md) 외에도 [Publishing Grammars 공식 가이드](https://ohmjs.org/docs/publishing-grammars)에서 "그래머는 API다"라는 철학을 다루는데, 이 파일이 그 철학을 실천하는 예시이기도 합니다.)

### 1.1 `space` 규칙을 완전히 새로 정의하기

```
space := whitespace | lineTerminator | comment
```

[02번 문서](./02-Ohm-문법-가이드.md)와 [08번 문서](./08-실전-팁과-주의사항.md)에서 주석을 공백처럼 다루는 방법으로 `space += comment`(확장)를 배웠습니다. 그런데 여기서는 `+=`가 아니라 **`:=`(덮어쓰기)** 를 쓰고 있습니다.

이유는 간단합니다. Ohm 내장 `space` 규칙은 ASCII 공백류만 인식하는데, JavaScript는 공백으로 취급해야 할 것이 유니코드 공백, 여러 종류의 줄바꿈 문자, 그리고 주석까지 훨씬 많습니다. 그래서 아예 처음부터 `whitespace | lineTerminator | comment`로 통째로 다시 정의한 것입니다. `+=`를 썼다면 `whitespace | lineTerminator | comment | 기존space정의`가 되어 중복이 생겼을 것입니다.

주목할 점은 `whitespace`와 `lineTerminator`를 **하나로 합치지 않고 별도 규칙으로 나눠뒀다**는 것입니다. 그 이유는 뒤에서 다룰 자동 세미콜론 삽입(ASI) 로직이 "공백이냐 아니냐"가 아니라 **"줄바꿈이 있었느냐"** 를 구체적으로 구분해야 하기 때문입니다. 즉 `space`는 이 둘을 합쳐서 공백 스킵용으로 쓰지만, `lineTerminator`는 다른 규칙에서 독립적으로도 참조됩니다.

### 1.2 식별자와 예약어 — 부정 lookahead의 실전 사용

```
identifier (an identifier) = ~reservedWord identifierName
```

[08번 문서](./08-실전-팁과-주의사항.md)에서 배운 "예약어가 식별자로 오인되지 않게 막는" 패턴이 그대로 등장합니다. `~reservedWord`(reservedWord가 아닐 때만)로 `if`, `while` 같은 키워드가 변수명으로 쓰이는 것을 막습니다.

`(an identifier)`처럼 규칙 이름 뒤에 괄호가 붙은 건 [02번 문서](./02-Ohm-문법-가이드.md)의 **규칙 설명(rule description)** 입니다. 나머지 규칙들에도 `(a digit)`, `(a Unicode combining mark)`처럼 자연어 설명이 붙어있는데, 이건 파싱이 실패했을 때 "identifier가 필요합니다" 같은 사람이 읽기 좋은 에러 메시지를 만들어주기 위한 장치입니다.

흥미로운 부분은 내장 규칙을 확장하는 코드입니다.

```
letter += unicodeCategoryNl
```

Ohm이 기본 제공하는 `letter` 규칙(대소문자 알파벳)에, JavaScript 식별자에 쓸 수 있는 특수 유니코드 문자 카테고리(`unicodeCategoryNl`, 로마 숫자 등)를 **추가**하고 있습니다. `+=` 연산자가 내장 규칙(`BuiltInRules`)에도 똑같이 적용될 수 있다는 걸 보여주는 좋은 사례입니다.

### 1.3 키워드를 규칙으로 캡슐화하는 패턴

```
break = "break" ~identifierPart
do = "do" ~identifierPart
instanceof = "instanceof" ~identifierPart
...
```

30개가 넘는 예약어 각각이 이런 식으로 **개별 규칙**으로 정의되어 있습니다. `~identifierPart`는 [08번 문서](./08-실전-팁과-주의사항.md)에서 배운 "예약어가 다른 식별자의 접두어가 되는 문제"를 막는 패턴입니다. 예를 들어 `in = "in" ~identifierPart`가 없다면 `instanceof`나 `inProgress`를 파싱하다가 `in` 규칙이 먼저 매칭돼버리는 문제가 생깁니다.

이렇게 **각 키워드를 규칙으로 만든 이유**는 두 가지입니다.

1. 문법 다른 곳에서 `if`, `while`, `for` 같은 이름을 마치 언어의 일부인 것처럼 자연스럽게 재사용할 수 있습니다 (`IfStatement = if "(" Expression<withIn> ")" Statement ...`처럼).
2. 나중에 시맨틱 액션을 붙일 때, 규칙 이름 자체가 이미 의미를 담고 있어서 코드가 읽기 쉬워집니다.

그리고 문법 파일 안에는 이런 주석이 있습니다.

```
// Note: keywords that are the complete prefix of another keyword should
// be prioritized (e.g. 'in' should come before 'instanceof')
```

[02번 문서](./02-Ohm-문법-가이드.md)에서 배운 대로, Ohm의 선택(`|`)은 **순서대로 시도해서 처음 성공하는 것을 채택**합니다. 그래서 `keyword` 규칙에서 `in`이 `instanceof`보다 먼저 나오면, `"instanceof"`라는 입력에서 `in`이 먼저 매칭되어버릴 위험이 있습니다. (다행히 위의 `~identifierPart` 덕분에 실제로는 문제가 생기지 않지만, 문법을 설계할 때 이 순서를 항상 의식해야 한다는 교훈을 주는 주석입니다.)

### 1.4 숫자 리터럴 — 선택 순서가 의미를 바꾸는 사례

```
numericLiteral = octalIntegerLiteral | hexIntegerLiteral | decimalLiteral
```

문법 파일에 이런 설명이 붙어있습니다.

> 명세와 반대로 `hexIntegerLiteral`을 `decimalLiteral`보다 앞에 둔 것은 의도적이다. `decimalLiteral | hexIntegerLiteral` 순서였다면 `"0x1F"`를 파싱할 때 `decimalLiteral`이 먼저 `"0"`만 소비해버리고, 남은 `"x1F"`를 별개로 처리하려 들었을 것이다.

이건 [02번 문서](./02-Ohm-문법-가이드.md)에서 다룬 "PEG의 선택은 더 긴 것을 우선하지 않고, 순서상 처음 성공하는 것을 채택한다"는 특성이 실제로 버그를 유발할 뻔한 사례입니다. 숫자 리터럴처럼 접두어가 겹치는 문법을 설계할 때는 **더 구체적인(긴 접두어를 요구하는) 규칙을 먼저** 배치해야 한다는 걸 실전 코드로 보여줍니다.

### 1.5 문자열과 이스케이프 시퀀스 — 구분 문자열 패턴의 확장판

```
stringLiteral = "\"" doubleStringCharacter* "\""
              | "'" singleStringCharacter* "'"
doubleStringCharacter = ~("\"" | "\\" | lineTerminator) sourceCharacter -- nonEscaped
                      | "\\" escapeSequence                             -- escaped
                      | lineContinuation                                -- lineContinuation
```

[08번 문서](./08-실전-팁과-주의사항.md)에서 배운 `구분자 (~구분자 any)* 구분자` 패턴의 확장판입니다. 여기서는 단순히 "닫는 따옴표가 아닌 아무 문자"가 아니라, **세 가지 경우를 명시적으로 나눠서** `-- nonEscaped`, `-- escaped`, `-- lineContinuation`이라는 케이스 이름을 붙였습니다.

- `nonEscaped`: 따옴표도, 백슬래시도, 줄바꿈도 아닌 평범한 문자
- `escaped`: 백슬래시로 시작하는 이스케이프 시퀀스 (`\n`, `\t`, `\uXXXX` 등)
- `lineContinuation`: 문자열 안에서 줄 끝에 백슬래시를 써서 다음 줄로 이어가는 JS 특유의 문법

이렇게 케이스를 나눠두면, 나중에 시맨틱 액션에서 "이스케이프된 문자는 실제 문자로 변환하고, 일반 문자는 그대로 둔다"처럼 케이스별로 다른 처리를 하기가 쉬워집니다. ([03번 문서](./03-시맨틱-액션과-오퍼레이션.md)에서 배운 `-- caseName`이 왜 유용한지 보여주는 좋은 예시입니다.)

### 1.6 자동 세미콜론 삽입(ASI) — `sc` 규칙 완전 분석

이 문법에서 가장 흥미로운 부분입니다. JavaScript는 문장 끝에 세미콜론을 생략해도 되는 경우가 있는데(Automatic Semicolon Insertion), 이 규칙 하나로 그 동작을 구현합니다.

```
sc = space* (";" | end)
   | spacesNoNL (lineTerminator | ~multiLineCommentNoNL multiLineComment | &"}")
```

두 개의 선택지로 나뉩니다.

**첫 번째 분기**: `space* (";" | end)` — 공백을 얼마든지 건너뛴 뒤에, 명시적인 세미콜론이 있거나 아예 입력이 끝나면 성공. 가장 단순한 경우입니다.

**두 번째 분기**: 세미콜론이 없어도 되는 경우들을 나열합니다.
- `spacesNoNL` 뒤에 `lineTerminator`가 오는 경우: 즉 줄바꿈 문자 자체를 만나면, "여기서 문장이 끝났다"고 간주(ASI 발동)
- `~multiLineCommentNoNL multiLineComment`: 줄바꿈을 포함하지 않는 여러 줄 주석은 건너뛰고, 줄바꿈을 포함한 주석이 나오면 그것도 ASI 신호로 취급
- `&"}"`: 다음에 닫는 중괄호가 온다면(lookahead로 소비하지 않고 확인만), 그 자리에서 문장이 끝났다고 간주

여기서 `spacesNoNL`이라는 **별도 규칙**을 정의한 이유가 나옵니다.

```
spacesNoNL = (whitespace | singleLineComment | multiLineCommentNoNL)*
```

이 규칙은 "줄바꿈은 포함하지 않는 공백류"만 건너뛰는 규칙입니다. 왜 필요할까요? ASI 로직 자체가 "줄바꿈이 있었는지 없었는지"를 정확히 알아야 하는데, 만약 그냥 평범한 `space*`(줄바꿈 포함)로 건너뛰어버리면 줄바꿈이 있었는지 이미 사라진 뒤라 판단할 수 없게 됩니다. 그래서 "줄바꿈만 빼고 건너뛰기" 전용 규칙을 별도로 만든 것입니다. 이것도 [02번 문서](./02-Ohm-문법-가이드.md)의 "space 규칙 커스터마이징" 개념이 실전에서 왜 필요한지 보여주는 사례입니다.

그리고 문법 파일에는 이런 중요한 주석이 있습니다.

```
// NOTE: Applications of this rule *must* appear in a lexical context -- either in the body of a
// lexical rule, or inside `#()`.
```

`sc`는 소문자로 시작하는 **어휘 규칙**입니다. 그런데 이 규칙이 실제로 쓰이는 곳(`VariableStatement`, `ReturnStatement` 등)은 전부 **대문자로 시작하는 구문 규칙**입니다. 구문 규칙 안에서는 공백이 자동으로 스킵된다는 걸 [02번 문서](./02-Ohm-문법-가이드.md)에서 배웠죠. 문제는 `sc`가 스스로 "줄바꿈이 있었는지"를 정밀하게 판단해야 하는데, 구문 규칙의 자동 공백 스킵이 먼저 개입해버리면 그 정밀한 판단이 무너집니다. 그래서 `sc`를 호출하는 모든 곳에서 반드시 `#sc`처럼 **어휘화 연산자(`#`)** 로 감싸서, 자동 공백 스킵을 끄고 `sc` 규칙이 직접 공백/줄바꿈을 통제하게 만듭니다.

```
VariableStatement = var VariableDeclarationList<withIn> #sc
```

이 한 줄이 바로 그 예시입니다. `#sc`가 아니라 그냥 `sc`였다면, `VariableStatement`가 구문 규칙이므로 `sc` 앞의 줄바꿈이 미리 건너뛰어져서 ASI 판단이 왜곡됐을 것입니다.

### 1.7 후위 연산자와 줄바꿈의 관계

```
PostfixExpression = LeftHandSideExpression #(spacesNoNL "++")  -- postIncrement
                  | LeftHandSideExpression #(spacesNoNL "--")  -- postDecrement
                  | LeftHandSideExpression
```

JavaScript에는 이런 함정이 있습니다.

```js
return
x++
```

이건 `return x++;`가 아니라 `return; x++;`로 해석됩니다(ASI 때문에 `return` 뒤에서 문장이 끊깁니다). 이 규칙은 그 규칙을 구현합니다. `#(spacesNoNL "++")`는 "줄바꿈 없이 공백만 건너뛴 뒤에 `++`가 와야 후위 증가 연산자로 인정한다"는 뜻입니다. 즉 `x`와 `++` 사이에 줄바꿈이 있으면 이 분기가 실패하고, 마지막 분기(그냥 `LeftHandSideExpression`)로 넘어가서 `++`는 다음 문장의 시작으로 남겨집니다.

## 2부: 표현식 문법 — 연산자 우선순위의 끝판왕

[04번 문서](./04-실전-예제-계산기-만들기.md)와 [08번 문서](./08-실전-팁과-주의사항.md)에서 "낮은 우선순위 규칙이 높은 우선순위 규칙을 호출하는 좌재귀 계층 구조"를 배웠습니다. 계산기에서는 딱 2단계(`AddExp` → `MulExp`)였지만, 실제 JavaScript는 훨씬 깊습니다.

| 단계 (우선순위 낮음 → 높음) | 규칙 이름 | 연산자 예시 |
|---|---|---|
| 1 | `Expression` | `,` (콤마 연산자) |
| 2 | `AssignmentExpression` | `=`, `+=`, `*=` 등 |
| 3 | `ConditionalExpression` | `? :` (삼항 연산자) |
| 4 | `LogicalORExpression` | `\|\|` |
| 5 | `LogicalANDExpression` | `&&` |
| 6 | `BitwiseORExpression` | `\|` |
| 7 | `BitwiseXORExpression` | `^` |
| 8 | `BitwiseANDExpression` | `&` |
| 9 | `EqualityExpression` | `==`, `!=`, `===`, `!==` |
| 10 | `RelationalExpression` | `<`, `>`, `<=`, `>=`, `instanceof`, `in` |
| 11 | `ShiftExpression` | `<<`, `>>`, `>>>` |
| 12 | `AdditiveExpression` | `+`, `-` |
| 13 | `MultiplicativeExpression` | `*`, `/`, `%` |
| 14 | `UnaryExpression` | `!`, `~`, 전위 `++`/`--`, `typeof`, `void`, `delete` |
| 15 | `PostfixExpression` | 후위 `++`/`--` |
| 16 | `LeftHandSideExpression` | 함수 호출, `new` |
| 17 | `PrimaryExpression` | 리터럴, 식별자, `(...)`, 배열/객체 리터럴 |

각 단계가 그 아래 단계를 호출하는 구조가 사슬처럼 이어지면서, 딱 한 번의 좌재귀 패턴이 17번 반복되는 셈입니다. 예를 들어 `AdditiveExpression`을 봅시다.

```
AdditiveExpression = AdditiveExpression "+" MultiplicativeExpression -- add
                   | AdditiveExpression "-" MultiplicativeExpression -- sub
                   | MultiplicativeExpression
```

[04번 문서](./04-실전-예제-계산기-만들기.md)에서 만든 계산기 문법과 형태가 완전히 동일합니다. 규모만 커졌을 뿐, 원리는 똑같다는 걸 확인할 수 있습니다.

### 2.1 `LeftHandSideExpression`의 상호 재귀 — `new`와 함수 호출

이 부분은 조금 특이합니다.

```
MemberExpression = MemberExpression "[" Expression<withIn> "]"  -- arrayRefExp
                 | MemberExpression "." identifierName  -- propRefExp
                 | new MemberExpression Arguments       -- newExp
                 | FunctionExpression
                 | PrimaryExpression

NewExpression = MemberExpression
              | new NewExpression -- newExp

CallExpression = CallExpression "[" Expression<withIn> "]"  -- arrayRefExp
               | CallExpression "." identifierName  -- propRefExp
               | CallExpression Arguments           -- callExpExp
               | MemberExpression Arguments         -- memberExpExp

LeftHandSideExpression = CallExpression
                       | NewExpression
```

`MemberExpression`과 `CallExpression`이 서로를 참조하며 **상호 재귀**를 이룹니다. 이렇게 복잡하게 나뉜 이유는 `new`가 붙었을 때와 안 붙었을 때 괄호(함수 호출 인자)의 의미가 미묘하게 다르기 때문입니다.

- `new Foo()` → `Foo`를 생성자로 호출 (이건 `MemberExpression`의 `newExp` 분기 + `Arguments`)
- `new Foo` → 괄호 없이도 `new` 가능 (`NewExpression`의 `newExp` 분기, `Arguments` 없음)
- `foo()` → 그냥 함수 호출 (`CallExpression`의 `memberExpExp` 분기)
- `new Foo().bar()` → `new Foo()`까지 만든 다음 그 결과에 `.bar()` 호출 (`CallExpression`이 `MemberExpression Arguments`로 시작해서, 그 뒤에 다시 `CallExpression`의 `propRefExp`, `callExpExp` 분기로 이어짐)

이렇게 규칙을 세분화한 이유는, JavaScript 명세 자체가 "new의 인자 목록이 어디까지인가"를 문법 레벨에서 엄밀하게 구분해야 하기 때문입니다. 실전 문법에서는 이렇게 개념적으로 하나처럼 보이는 것(함수/생성자 호출)도, 명세의 모호함을 없애기 위해 규칙을 여러 개로 쪼개는 경우가 흔하다는 걸 보여주는 사례입니다.

### 2.2 매개변수화된 규칙으로 문맥 의존 문법 해결하기 — `noIn`/`withIn`

여기가 이 문법에서 가장 정교한 부분입니다. JavaScript에는 이런 모호함이 있습니다.

```js
for (a in b) { ... }        // "a in b"라는 하나의 표현식을 순회하는 for-in 문
for (a; a in b; a++) { ... } // 세미콜론으로 구분된 일반 for 문, 조건절에 "a in b" 등장
```

두 번째 예시에서 `for (a` 다음에 등장하는 `in`이 진짜 `for-in`의 `in`인지, 아니면 `RelationalExpression`의 `in` 연산자인지 파서 입장에서는 헷갈릴 수 있습니다. 명세는 이 문제를 "특정 문맥에서는 `in` 연산자를 문법적으로 금지한다"는 규칙으로 해결하는데, Ohm은 이걸 **매개변수화된 규칙**으로 정확히 표현합니다.

```
RelationalExpression<guardIn>
  = ...
  | RelationalExpression<guardIn> guardIn "in" ShiftExpression  -- inExp
  | ShiftExpression
```

`guardIn`이라는 매개변수를 받아서, `in` 연산자 앞에 `guardIn` 자체를 끼워 넣었습니다. 이 매개변수 자리에 실제로 들어가는 값은 둘 중 하나입니다.

```
noIn = ~in
withIn =
```

- `withIn`은 **빈 시퀀스**입니다. 아무 것도 매칭하지 않고 항상 성공합니다. 즉 `guardIn`이 `withIn`으로 치환되면, `in` 연산자 앞에 "항상 성공하는 아무것도 아닌 것"이 끼워지므로 사실상 `in` 연산자가 평소처럼 허용됩니다.
- `noIn`은 `~in`, 즉 "다음에 `in`이 오면 안 된다"는 부정 lookahead입니다. `guardIn`이 `noIn`으로 치환되면, `in` 연산자 앞에서 이 lookahead가 걸려서 사실상 **`in` 연산자를 이 문맥에서는 금지**시킵니다.

그리고 이 매개변수는 `RelationalExpression`에서 끝나지 않고, 그 위의 모든 우선순위 단계(`EqualityExpression<guardIn>`, `BitwiseANDExpression<guardIn>`, ..., `Expression<guardIn>`)로 계속 전파됩니다. 실제 `for` 문에서 이 매개변수가 어떻게 쓰이는지 봅시다.

```
IterationStatement = ...
  | for "(" Expression<noIn>? ";"
              Expression<withIn>? ";"
              Expression<withIn>? ")" Statement          -- for3
  | ...
  | for "(" LeftHandSideExpression in
              Expression<withIn> ")" Statement           -- forIn
  | ...
```

`for3`(일반 for 문)의 **첫 번째** `Expression`(초기화절)만 `<noIn>`이고, 나머지는 전부 `<withIn>`입니다. 정확히 `for (` 바로 다음, 세미콜론이 나오기 전까지의 구간에서만 `in`을 금지하는 것이죠. 이것이야말로 [02번 문서](./02-Ohm-문법-가이드.md)에서 배운 "매개변수화된 규칙으로 고차 규칙을 만들 수 있다"는 설명이 실제로 어떤 위력을 발휘하는지 보여주는 최고의 예시입니다. 같은 `RelationalExpression` 규칙 하나로, 문맥에 따라 동작이 달라지는 문법을 **규칙을 복제하지 않고** 표현한 것입니다.

## 3부: 문(Statement)과 그래머 상속

### 3.1 `IterationStatement`의 4가지 for 변형

```
IterationStatement = do Statement while "(" Expression<withIn> ")" #sc  -- doWhile
                   | while "(" Expression<withIn> ")" Statement           -- whileDo
                   | for "(" Expression<noIn>? ";" ... ")" Statement       -- for3
                   | for "(" var VariableDeclarationList<noIn> ";" ... ")" Statement -- for3var
                   | for "(" LeftHandSideExpression in Expression<withIn> ")" Statement -- forIn
                   | for "(" var VariableDeclaration<noIn> in Expression<withIn> ")" Statement -- forInVar
```

`for` 문만 4가지 케이스(`for3`, `for3var`, `forIn`, `forInVar`)로 나뉘어 있습니다. `var` 선언이 있는지 없는지, 세미콜론 방식인지 `in` 방식인지에 따라 각각 케이스 이름을 붙여서 구분한 것입니다. 이렇게 자잘하게 나눠두면 [03번 문서](./03-시맨틱-액션과-오퍼레이션.md)에서 배운 대로, 시맨틱 액션을 작성할 때 각 케이스마다 정확히 필요한 처리를 따로 작성할 수 있어서 매우 편리해집니다. (반대로 하나로 뭉뚱그려 놨다면, 시맨틱 액션 안에서 "이게 var가 있는 경우인가?"를 직접 분기해야 해서 코드가 지저분해졌을 것입니다.)

### 3.2 그래머 상속으로 strict/non-strict 모드 구현하기

문법 파일 맨 마지막 줄입니다.

```
ES5Lax <: ES5 {
  futureReservedWord := futureReservedWordLax
}
```

[02번 문서](./02-Ohm-문법-가이드.md)와 [05번 문서](./05-API-레퍼런스.md)에서 배운 **그래머 상속**의 실전 사용례입니다. JavaScript strict mode에서는 `implements`, `let`, `yield` 같은 단어들도 예약어로 취급되지만, non-strict(lax) 모드에서는 예약어가 아닙니다. `ES5` 문법은 다음처럼 정의되어 있었죠.

```
futureReservedWordStrict = futureReservedWordLax
                         | implements | let     | private   | public
                         | interface  | package | protected | static
                         | yield

futureReservedWord = futureReservedWordStrict
```

`ES5Lax`는 이 `ES5` 전체를 상속받은 뒤, **딱 한 줄**로 `futureReservedWord` 규칙만 `futureReservedWordLax`(더 짧은 예약어 목록)로 덮어씁니다(`:=`). 100개가 넘는 나머지 규칙은 전혀 손대지 않고 그대로 재사용됩니다.

이게 바로 [00번 문서](./00-목차.md)에서 언급했던 "그래머는 API다"라는 Ohm의 철학이 실전에서 발휘되는 순간입니다. 문법 전체를 복사-붙여넣기해서 살짝 고치는 대신, **상속과 오버라이드**로 "거의 같지만 한 군데만 다른 언어"를 아주 적은 코드로 표현할 수 있습니다.

## 4부: 시맨틱 액션 ① — 원본 소스 완전 재구성하기 (`toES5`)

이제 `es5.js`로 넘어갑니다. 첫 번째 오퍼레이션 `toES5()`는 파스 트리를 다시 원본과 **완전히 동일한 소스 코드 문자열**로 재구성합니다. 공백, 줄바꿈, 주석까지 한 글자도 빠짐없이 복원합니다.

### 4.1 왜 이런 오퍼레이션이 필요한가

당연히 `match()`에 넣었던 원본 문자열을 그냥 그대로 돌려주면 되는 거 아니냐고 생각할 수 있습니다. 하지만 이 오퍼레이션의 진짜 목적은 **파스 트리를 변형한 뒤에 다시 소스 코드로 되돌리는 것**입니다. 예를 들어 특정 노드만 골라서 다른 값으로 바꿔치기하거나, 코드의 일부를 변환하는 도구(코드 모드, 트랜스파일러, 자동 리팩터링 도구 등)를 만들 때, "고치지 않은 부분은 원본 그대로, 고친 부분만 바뀐 형태로" 출력해야 합니다. 이런 도구의 뼈대가 되는 것이 바로 이 `toES5` 패턴입니다.

### 4.2 핵심 재료: `source` Interval

[05번 문서](./05-API-레퍼런스.md)의 파스 노드 표에서 `n.source`(소비한 입력 구간)와 `n.sourceString`을 배웠습니다. 이 오퍼레이션은 그중에서도 `n.source.startIdx`, `n.source.endIdx`(구간의 시작/끝 인덱스)를 적극적으로 활용합니다.

왜 `sourceString`을 그냥 이어붙이면 안 될까요? 구문 규칙(대문자 규칙)은 자식들 **사이의 공백을 자동으로 스킵**하기 때문에, 파스 트리 자체에는 공백 정보가 온전히 남아있지 않습니다(정확히는, 공백을 소비하긴 하지만 각 자식 노드의 `sourceString`에는 포함되지 않습니다). 그래서 자식들의 `sourceString`을 단순히 이어붙이면 원본에 있던 공백과 줄바꿈, 주석이 모두 사라져버립니다. 이 문제를 해결하려면 "이 자식이 끝난 지점부터 다음 자식이 시작하는 지점 사이"의 원본 문자열을 직접 잘라내서 끼워 넣어야 합니다. 그게 이 오퍼레이션의 핵심 아이디어입니다.

### 4.3 `flattenIterNodes` — 반복 노드 평탄화하기

```js
function flattenIterNodes(nodes) {
  const result = [];
  for (let i = 0; i < nodes.length; ++i) {
    if (nodes[i]._node.ctorName === '_iter') {
      result.push(...flattenIterNodes(nodes[i].children));
    } else {
      result.push(nodes[i]);
    }
  }
  return result;
}
```

[03번 문서](./03-시맨틱-액션과-오퍼레이션.md)에서 배운 반복 노드(iteration node) 개념을 떠올려보세요. `StatementList = Statement*`처럼 `*`나 `+`로 만들어진 자식은 그 자체로 하나의 "반복 노드"이고, 그 반복 노드 밑에 실제 자식들(개별 `Statement`들)이 들어있습니다.

`_nonterminal` 액션이 `...children`으로 자식들을 받을 때, 그중 일부는 평범한 노드고 일부는 이런 반복 노드일 수 있습니다. `flattenIterNodes`는 [05번 문서](./05-API-레퍼런스.md)에서 배운 `n.ctorName` 속성으로 "이 자식이 반복 노드인가"(`ctorName === '_iter'`)를 확인하고, 맞다면 그 안의 진짜 자식들을 재귀적으로 꺼내서 평평한(flat) 배열로 만듭니다. 재귀적으로 처리하는 이유는 반복 노드 안에 또 반복 노드가 중첩될 수 있기 때문입니다(예: `(x ",")*` 같은 구조).

### 4.4 `compareByInterval` — 소스 순서대로 정렬하기

```js
function compareByInterval(node, otherNode) {
  return node.source.startIdx - otherNode.source.startIdx;
}
```

왜 정렬이 필요할까요? 시맨틱 액션의 인자 순서가 항상 원본 소스에 나온 순서와 일치한다는 보장이 없기 때문입니다. 특히 [2부](#2부-표현식-문법--연산자-우선순위의-끝판왕)에서 본 `guardIn` 같은 매개변수는 실제 소스에는 존재하지 않는 "빈 값"(`withIn =`처럼 아무것도 매칭하지 않는 시퀀스)일 수도 있고, 여러 파라미터가 섞이면서 자식 노드들의 배열 순서가 뒤섞일 가능성이 있습니다. `startIdx` 기준으로 다시 정렬해두면, 실제로 코드를 출력할 때 항상 원본 순서를 보장할 수 있습니다.

### 4.5 `nodeToES5` — 실제 복원 로직

```js
function nodeToES5(node, children) {
  const flatChildren = flattenIterNodes(children).sort(compareByInterval);
  let prevEndIdx = node.source.startIdx;
  let code = '';
  for (let i = 0; i < flatChildren.length; ++i) {
    const child = flatChildren[i];
    if (child.source.startIdx > prevEndIdx) {
      code += node.source.sourceString.slice(prevEndIdx, child.source.startIdx);
    }
    code += child.toES5();
    prevEndIdx = child.source.endIdx;
  }
  return code;
}
```

한 줄씩 뜯어보면 다음과 같습니다.

1. `flattenIterNodes` + `sort`로 반복 노드를 풀고 소스 순서대로 정렬한 `flatChildren`을 준비합니다.
2. `prevEndIdx`를 `node.source.startIdx`(현재 노드 전체가 시작하는 위치)로 초기화합니다. 이건 "지금까지 처리한 지점"을 추적하는 커서입니다.
3. 각 자식을 순회하면서, **이전 자식이 끝난 지점(`prevEndIdx`)부터 지금 자식이 시작하는 지점(`child.source.startIdx`) 사이에 간격이 있다면**, 그 사이의 원본 문자열을 그대로 잘라내서(`node.source.sourceString.slice(...)`) 복원합니다. 이 간격이 바로 공백, 줄바꿈, 주석이 있던 자리입니다.
4. 그 다음 `child.toES5()`를 재귀 호출해서 그 자식 노드 자체를 (하위 트리까지 재귀적으로) 문자열로 바꿔서 이어붙입니다.
5. `prevEndIdx`를 `child.source.endIdx`로 갱신하고 다음 자식으로 넘어갑니다.

이 로직 덕분에, 자식 노드 자체는 각자 자기 부분만 책임지고, **자식과 자식 "사이"의 여백**은 항상 부모 노드가 원본에서 그대로 복원해주는 구조가 만들어집니다. 트리 전체에 대해 이 과정이 재귀적으로 일어나면 결과적으로 "원본과 100% 동일한 문자열"이 만들어지는 것입니다. 이런 방식을 흔히 **무손실(lossless) 변환**이라고 부릅니다.

### 4.6 오퍼레이션 조립하기

```js
semantics.addOperation('toES5()', {
  Program(_, sourceElements) {
    const {sourceString} = this.source;
    return (
      sourceString.slice(0, this.source.startIdx) +
      nodeToES5(this, [sourceElements]) +
      sourceString.slice(this.source.endIdx)
    );
  },
  _nonterminal(...children) {
    return nodeToES5(this, children);
  },
  _terminal() {
    return this.sourceString;
  },
});
```

가장 놀라운 부분은, **문법에 있는 100개가 넘는 규칙 중 단 하나(`Program`)를 제외하고는 규칙별 액션을 전혀 작성하지 않았다**는 점입니다. [03번 문서](./03-시맨틱-액션과-오퍼레이션.md)에서 배운 특수 액션 `_nonterminal`과 `_terminal`이 각각 다음을 담당합니다.

- `_terminal()`: 터미널 노드(문자열 리터럴 등)는 그냥 `this.sourceString`을 그대로 반환하면 됩니다. 더 분해할 것이 없으니까요.
- `_nonterminal(...children)`: 모든 논터미널 노드(즉 규칙 이름이 붙은 대부분의 노드)에 대해 앞서 만든 `nodeToES5` 헬퍼를 그대로 적용합니다. 규칙이 무엇이든 상관없이 "자식들을 원본 순서대로 이어붙이고 그 사이 공백을 복원한다"는 로직은 동일하기 때문에, 이 하나의 기본 동작으로 모든 규칙이 커버됩니다.

`Program`만 예외인 이유는, `Program`은 **트리 전체의 최상위 노드**이기 때문입니다. `nodeToES5` 로직은 "자식과 자식 사이"의 공백만 복원할 뿐, 트리의 **맨 앞과 맨 뒤**(즉 최상위 노드 자체의 시작 이전, 끝 이후)에 있는 공백은 애초에 어떤 자식-자식 사이도 아니므로 복원 대상이 아닙니다. 그래서 `Program` 액션에서 별도로 `sourceString.slice(0, this.source.startIdx)`(맨 앞의 여백)와 `sourceString.slice(this.source.endIdx)`(맨 뒤의 여백)를 직접 붙여줍니다.

이 설계는 [03번 문서](./03-시맨틱-액션과-오퍼레이션.md)에서 이야기했던 "문법이 아무리 커도, 공통 패턴이 있다면 `_nonterminal` 하나로 왕창 처리할 수 있다"는 원칙을 가장 극적으로 보여주는 사례입니다. 규칙이 100개든 1000개든, 이 시맨틱은 여전히 3개의 액션만으로 충분합니다.

## 5부: 시맨틱 액션 ② — 변수/함수 호이스팅 분석하기 (`hoistDeclarations`)

두 번째 오퍼레이션은 JavaScript의 **호이스팅**(hoisting) — `var`와 함수 선언이 스코프 최상단으로 끌어올려지는 특성 — 을 분석해서, "이 코드 블록 안에 어떤 이름들이 선언되어 있는가"를 찾아냅니다.

### 5.1 오퍼레이션 정의

```js
semantics.addOperation('hoistDeclarations()', {
  FunctionDeclaration(_, ident, _1, _2, _3, _4, _5, _6) {
    return new Map([[ident.sourceString, [ident.source]]]);
  },
  FunctionExpression(_) {
    return new Map();
  },
  VariableDeclaration(ident, _) {
    return new Map([[ident.sourceString, [ident.source]]]);
  },
  _iter: mergeBindings,
  _nonterminal: mergeBindings,
  _terminal() {
    return new Map();
  },
});
```

이 오퍼레이션의 결과 타입은 **`Map<식별자이름, 소스위치배열>`** 입니다. "어떤 이름이, 소스 코드의 어느 위치(들)에서 선언되었는가"를 알려줍니다.

### 5.2 왜 `FunctionDeclaration`은 내부를 재귀하지 않는가

```js
FunctionDeclaration(_, ident, _1, _2, _3, _4, _5, _6) {
  return new Map([[ident.sourceString, [ident.source]]]);
}
```

인자가 8개(`_`, `ident`, `_1`~`_6`)나 되는 건 `FunctionDeclaration` 규칙의 본문이 `function identifier "(" FormalParameterList ")" "{" FunctionBody "}"`로 8개 부분을 갖기 때문입니다. 그런데 이 액션은 `ident`(함수 이름)만 사용하고, **함수 본문(`FunctionBody`, 즉 `_6`)은 아예 재귀 호출하지 않습니다.**

이건 의도적인 설계입니다. 함수 선언 자체는 "이 스코프에 `foo`라는 이름이 있다"는 사실 하나만 바깥 스코프에 알리면 됩니다. 함수 **내부**에서 어떤 `var`가 선언되든, 그건 그 함수만의 스코프에 속하는 얘기지 바깥 스코프로 호이스팅될 대상이 아닙니다. 그래서 이 오퍼레이션은 함수 경계에서 재귀를 의도적으로 멈춥니다.

코드 주석에도 이렇게 적혀 있습니다.

> 이 오퍼레이션은 그 자체로 중첩된 렉시컬 환경(스코프)을 만들지는 않지만, 다른 오퍼레이션이 스코프를 만들 때 헬퍼로 활용할 수 있도록 설계되었다.

즉 `hoistDeclarations()`는 딱 "한 겹"만 담당합니다. 만약 정말로 스코프 체인 전체를 분석하는 도구를 만든다면, 이 오퍼레이션을 감싸는 **더 상위의 오퍼레이션**을 만들어서, `FunctionDeclaration`/`FunctionExpression`을 만날 때마다 새로운 스코프를 열고 그 안에서 다시 `hoistDeclarations()`를 호출하는 식으로 구성하면 됩니다. 이 오퍼레이션 자체가 그 재귀 진입점 역할을 할 수 있도록 일부러 얕게(shallow) 설계된 것입니다.

### 5.3 왜 `FunctionExpression`은 빈 Map을 반환하는가

```js
FunctionExpression(_) {
  return new Map();
}
```

`var foo = function bar() { ... }`처럼 함수 표현식에 이름(`bar`)이 붙어있는 경우가 있습니다. 하지만 이 이름은 JavaScript 명세상 **그 함수 자신의 내부에서만** 유효하고, 바깥 스코프로 호이스팅되지 않습니다. `FunctionDeclaration`과 미묘하게 다른 점입니다. 그래서 `FunctionExpression`은 (내부에 이름이 있든 없든) 바깥으로 아무 것도 호이스팅하지 않는다는 뜻에서 무조건 빈 `Map`을 반환합니다.

### 5.4 `VariableDeclaration`에서 초기화식은 왜 무시하는가

```js
VariableDeclaration(ident, _) {
  return new Map([[ident.sourceString, [ident.source]]]);
}
```

`VariableDeclaration = identifier Initialiser<guardIn>?`이므로 인자는 `ident`(식별자)와 `_`(선택적 초기화식, `= 값` 부분)입니다. `var x = someFunction()`이라는 코드가 있을 때, 호이스팅되는 건 오직 이름 `x`뿐이고, `someFunction()`이라는 **호출 자체**는 실행 시점에 평가되는 것이지 호이스팅과 무관합니다. 그래서 두 번째 인자(초기화식)는 아예 사용하지 않고 밑줄로 표시해서 "의도적으로 무시한다"는 걸 코드로 드러냅니다.

### 5.5 `mergeBindings` — `_iter`와 `_nonterminal`이 함수 하나를 공유하는 이유

```js
function mergeBindings(...nodes) {
  const bindings = new Map();
  for (const child of nodes.filter(c => !c.isLexical())) {
    child.hoistDeclarations().forEach((sources, ident) => {
      if (bindings.has(ident)) {
        bindings.get(ident).push(...sources); // Shadowed binding.
      } else {
        bindings.set(ident, sources); // Not shadowed at this level.
      }
    });
  }
  return bindings;
}
```

`_iter: mergeBindings`와 `_nonterminal: mergeBindings`처럼, 같은 함수를 두 특수 액션에 동시에 등록했습니다. [03번 문서](./03-시맨틱-액션과-오퍼레이션.md)에서 `_iter`와 `_nonterminal`은 둘 다 "임의 개수의 자식을 나머지 매개변수로 받는다"는 시그니처가 같다고 배웠는데, 그 덕분에 이렇게 완전히 동일한 함수를 재사용할 수 있습니다. "자식들의 호이스팅 결과를 전부 합친다"는 동작은 그 자식들이 반복 노드(`_iter`)에서 온 것이든, 일반 규칙(`_nonterminal`)에서 온 것이든 다를 이유가 없기 때문입니다.

`nodes.filter(c => !c.isLexical())`에서 처음 보는 메서드가 등장합니다. `isLexical()`은 노드를 만든 규칙이 **어휘 규칙(소문자로 시작하는 규칙)** 인지 확인하는 메서드로 보입니다. 예약어나 식별자 이름(`identifierName`), 각종 리터럴 파싱에 쓰이는 어휘 규칙들은 애초에 그 안에 `VariableDeclaration`이나 `FunctionDeclaration` 같은 구문 규칙이 등장할 수 없는 구조입니다. 이런 어휘 규칙 자식들까지 매번 `hoistDeclarations()`를 호출해서 순회하는 건 불필요한 작업이므로, 미리 걸러내서 불필요한 순회를 줄이는 최적화로 볼 수 있습니다.

나머지 로직은 표준적인 Map 병합입니다. 같은 이름이 이미 등록되어 있으면(즉 같은 이름이 여러 번 선언된 경우, JavaScript의 `var`는 이게 합법입니다) 위치 배열에 추가로 `push`하고, 처음 보는 이름이면 새로 등록합니다. 코드 주석의 `// Shadowed binding.`이라는 표현은, 이렇게 여러 위치를 배열로 남겨두면 나중에 "이 이름이 이 스코프에서 몇 번, 어디서 선언됐는지"를 그대로 추적할 수 있어서, 린팅 도구가 "같은 변수를 중복 선언했습니다" 같은 경고를 만드는 데 활용할 수 있다는 걸 시사합니다.

## 6부: 두 오퍼레이션을 실제로 사용해보기

`es5.js`가 `export {grammar, semantics}`로 내보낸 것을 가져와서 실제로 실행하면 다음과 같은 흐름이 됩니다.

```js
import {grammar, semantics} from './es5.js';

const source = `
  var x = 1;
  function foo() {
    var y = 2;
    return x + y;
  }
`;

const match = grammar.match(source);

if (match.succeeded()) {
  const result = semantics(match);

  // 1. 원본을 한 글자도 틀리지 않고 복원할 수 있는지 확인
  console.log(result.toES5() === source); // true

  // 2. 최상위 스코프에 호이스팅되는 이름들 확인
  console.log(result.hoistDeclarations());
  // Map(2) { 'x' => [Interval], 'foo' => [Interval] }
  // 주의: 'y'는 foo 함수 내부의 선언이므로 여기 포함되지 않음
} else {
  console.log(match.message);
}
```

`hoistDeclarations()`의 결과에 `y`가 포함되지 않는다는 점이 5부에서 설명한 "함수 경계에서 재귀를 멈춘다"는 설계가 실제로 어떻게 동작하는지를 잘 보여줍니다.

## 마무리

작은 계산기 문법에서 시작해서, 여기까지 오면서 확인한 건 결국 **Ohm의 핵심 개념 수가 많지 않다**는 사실입니다. 터미널, 반복, 선택, lookahead, 매개변수화된 규칙, 그래머 상속, 그리고 `_terminal`/`_nonterminal`/`_iter`라는 세 가지 특수 액션. 이 몇 가지 재료만으로 실제 프로그래밍 언어 하나를 통째로 파싱하고, 그 결과로 소스를 무손실 복원하거나 호이스팅 같은 의미론적 분석까지 해낼 수 있다는 것이, Ohm이 "작지만 강력하다"고 평가받는 이유입니다.
